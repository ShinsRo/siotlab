# Object Types

- JS 에서 데이터를 묶는 가장 기본적인 방법은 객체
- TS 에서는 객체 타입 (object types) 으로 이를 표현

```typescript
// 익명 객체 타입
function greet(person: { name: string; age: number }) { /* ... */ }

// 인터페이스로 이름 부여
interface Person { name: string; age: number; }
function greet(person: Person) { /* ... */ }

// 타입 별칭 (type alias) 으로도 가능
type Person = { name: string; age: number; };
```

## 프로퍼티 수정자 (Property Modifiers)

### 선택적 프로퍼티 (Optional Properties)

- 프로퍼티 이름 뒤에 `?` → 선택적
- 없어도 되며, 접근 시 타입은 `T | undefined`

```typescript
interface PaintOptions {
  shape: Shape;
  xPos?: number;
  yPos?: number;
}

function paintShape({ shape, xPos = 0, yPos = 0 }: PaintOptions) {
  // xPos, yPos: number (기본값이 있으니 undefined 제거됨)
}
```

- 구조 분해 시 기본값을 주면 `undefined` 를 제거할 수 있음
- 주의: 타입 어노테이션을 구조 분해 안에 붙이면 그건 rename 문법과 겹치므로 밖에 붙일 것

### `readonly` 프로퍼티

- 읽기 전용 프로퍼티. 재할당 불가
- 완전한 불변성은 아님 → 참조 객체 내부는 여전히 변경 가능

```typescript
interface SomeType { readonly prop: string; }

function doSomething(obj: SomeType) {
  console.log(obj.prop);
  obj.prop = "hello"; // error
}

interface Home { readonly resident: { name: string; age: number; }; }

function visit(home: Home) {
  home.resident.age++;              // OK (내부 프로퍼티는 readonly 아님)
  home.resident = { name: "..." };  // error
}
```

- 두 타입 사이의 `readonly` 여부 차이는 할당 가능성에 영향을 주지 않음 → 별칭을 통한 우회 변경이 가능

### 인덱스 시그니처 (Index Signatures)

- 프로퍼티 이름은 모르지만 값의 형태를 아는 경우 사용
- 인덱스 타입은 `string`, `number`, `symbol`, 템플릿 리터럴 패턴만 허용

```typescript
interface StringArray {
  [index: number]: string;
}

const myArray: StringArray = getStringArray();
const secondItem = myArray[1]; // string
```

- 인덱스 시그니처가 있으면, 명시된 다른 프로퍼티도 그 반환 타입과 호환되어야 함

```typescript
interface NumberDictionary {
  [index: string]: number;
  length: number;    // OK
  name: string;      // error: string 은 number 에 할당 불가
}
```

- 유니온으로 완화 가능

```typescript
interface NumberOrStringDictionary {
  [index: string]: number | string;
  length: number;
  name: string;
}
```

- 인덱스 시그니처를 `readonly` 로 지정하면 요소 재할당 방지 가능

## 초과 프로퍼티 검사 (Excess Property Checks)

- **객체 리터럴** 을 다른 변수에 할당하거나 인자로 전달할 때, 대상 타입에 없는 프로퍼티가 있으면 에러

```typescript
interface SquareConfig {
  color?: string;
  width?: number;
}

function createSquare(config: SquareConfig): { /* ... */ } { /* ... */ }

createSquare({ colour: "red", width: 100 });
// error: 'colour' 는 SquareConfig 에 없음 (아마 오타?)
```

- 우회 방법
    1. 타입 단언 사용: `... as SquareConfig`
    2. 인덱스 시그니처 추가
    3. **변수에 먼저 할당** → 초과 프로퍼티 검사 우회

```typescript
const squareOptions = { colour: "red", width: 100 };
const mySquare = createSquare(squareOptions); // OK (호환 프로퍼티가 있으므로)
```

## 타입 확장 (Extending Types)

- 인터페이스는 `extends` 로 확장 가능

```typescript
interface BasicAddress {
  name?: string;
  street: string;
  city: string;
  country: string;
  postalCode: string;
}

interface AddressWithUnit extends BasicAddress {
  unit: string;
}
```

- 여러 개 확장도 가능

```typescript
interface Colorful { color: string; }
interface Circle { radius: number; }
interface ColorfulCircle extends Colorful, Circle {}
```

## 교집합 타입 (Intersection Types)

- `&` 연산자로 여러 타입을 결합
- 결합된 모든 타입의 프로퍼티를 가짐

```typescript
type ColorfulCircle = Colorful & Circle;

function draw(circle: ColorfulCircle) {
  console.log(`color: ${circle.color}, radius: ${circle.radius}`);
}
```

## 인터페이스 vs. 교집합

- `interface extends` 와 `&` 는 비슷해 보이지만 미묘한 차이가 있음
- 인터페이스 확장 시 프로퍼티 충돌은 컴파일 에러 → 명확한 실패
- 교집합은 충돌해도 조용히 결합 → 결과 타입이 `never` 가 되는 경우 발생
- 그래서 대체로 인터페이스 확장을 선호하는 편이 안전

## 제네릭 객체 타입 (Generic Object Types)

- 어떤 값이든 담을 수 있는 컨테이너를 표현할 때
- `any` 는 안전하지 않음 → 타입 파라미터 사용

```typescript
interface Box<Type> {
  contents: Type;
}

const stringBox: Box<string> = { contents: "hello" };
const numberBox: Box<number> = { contents: 42 };
```

- 타입 별칭도 제네릭 가능

```typescript
type Box<Type> = { contents: Type; };
type OrNull<Type> = Type | null;
type OneOrMany<Type> = Type | Type[];
```

### `Array` 타입

- `number[]` / `string[]` 형태의 문법은 사실 `Array<number>` / `Array<string>` 의 축약형
- `Array` 자체가 제네릭

```typescript
interface Array<Type> {
  length: number;
  pop(): Type | undefined;
  push(...items: Type[]): number;
  // ...
}
```

- `Map<K, V>`, `Set<T>`, `Promise<T>` 등도 마찬가지로 제네릭

### `ReadonlyArray` 타입

- 변경 불가능한 배열을 표현
- 함수 파라미터로 받으면 그 함수가 배열을 변경하지 않겠다는 의도를 표현할 수 있음

```typescript
function doStuff(values: ReadonlyArray<string>) {
  values.push("hello!"); // error: push 없음
}
```

- `readonly Type[]` 축약 문법 가능
- `Array` 와 `ReadonlyArray` 는 양방향 할당 가능하지 않음
    - `Array` → `ReadonlyArray` : OK
    - `ReadonlyArray` → `Array` : error

### 튜플 타입 (Tuple Types)

- 요소 개수와 각 위치의 타입이 정확히 정해진 배열

```typescript
type StringNumberPair = [string, number];

function doSomething(pair: StringNumberPair) {
  const a = pair[0]; // string
  const b = pair[1]; // number
  const c = pair[2]; // error: 인덱스 2 없음
}
```

- 구조 분해와 잘 어울림

```typescript
function doSomething([inputString, hash]: [string, number]) { /* ... */ }
```

- 선택적 요소 (`?`) 도 가능 → 마지막에만

```typescript
type Either2dOr3d = [number, number, number?];
```

- rest 요소도 가능

```typescript
type StringNumberBooleans = [string, number, ...boolean[]];
type StringBooleansNumber = [string, ...boolean[], number];
type BooleansStringNumber = [...boolean[], string, number];
```

- 나머지 파라미터에도 튜플 타입 활용 가능

```typescript
function readButtonInput(...args: [string, number, ...boolean[]]) {
  const [name, version, ...input] = args;
}
```

### `readonly` 튜플 타입

- 튜플도 `readonly` 로 지정 가능 → 요소 변경 불가
- 배열 리터럴에 `as const` 를 붙이면 → 자동으로 `readonly` 튜플로 추론됨

```typescript
let point = [3, 4] as const; // readonly [3, 4]

function distanceFromOrigin([x, y]: [number, number]) { /* ... */ }
distanceFromOrigin(point);
// error: readonly [3, 4] 는 변경 가능한 [number, number] 에 할당 불가
```

- `distanceFromOrigin` 이 배열을 변경하지 않더라도, TS 는 시그니처를 신뢰함 → 파라미터 타입을 `readonly` 로 명시하는 편이 좋음
