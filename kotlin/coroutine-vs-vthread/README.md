# Coroutine vs Virtual Thread

코루틴과 가상 스레드를 비교할 때는 단순히 "더 빠른가"만 보면 부족하다. 이 문서는 두 모델을 어떤 기준으로 비교하면 좋은지 정리한 출발점이다.

## 비교 목적

코루틴과 가상 스레드는 모두 높은 동시성을 다루기 위한 도구이지만, 추구하는 모델이 다르다.

- 코루틴: 적은 비용의 비동기 태스크와 구조화된 동시성에 강점이 있다.
- 가상 스레드: 동기식 코드 스타일을 유지하면서 대규모 동시성을 처리하는 데 강점이 있다.

따라서 비교는 성능뿐 아니라 개발 모델, 운영 편의성, 생태계 호환성까지 포함해야 한다.

## 핵심 비교 지표

### 1. 성능 지표

- 처리량(Throughput)
  - 초당 몇 개의 작업을 처리할 수 있는가
- 지연시간(Latency)
  - 평균 응답 시간
  - p95, p99 같은 tail latency
- 동시성 규모(Concurrency Scale)
  - 동시 작업 수가 1천, 1만, 10만으로 늘어날 때 얼마나 안정적으로 유지되는가
- 메모리 사용량(Memory Footprint)
  - 작업 1개당 오버헤드
  - 전체 힙 사용량
- CPU 사용률(CPU Efficiency)
  - 같은 부하에서 CPU를 얼마나 효율적으로 사용하는가
- 컨텍스트 전환 비용(Context Switch Cost)
  - 작업 전환이 빈번할 때 비용이 얼마나 드는가

### 2. 워크로드별 특성

- 블로킹 I/O 대응력
  - `sleep`, 파일 I/O, DB 호출, HTTP 호출처럼 대기 시간이 긴 작업에서 어떤 특성을 보이는가
- CPU 바운드 작업 성능
  - 계산 위주의 작업에서 스케줄링 오버헤드가 얼마나 드는가
- 혼합형 워크로드 적합성
  - 짧은 계산과 외부 I/O가 섞인 상황에서 어느 쪽이 더 자연스럽고 안정적인가

### 3. 스케줄링과 안정성

- 공정성(Fairness)
  - 일부 작업이 과도하게 지연되거나 starvation이 발생하지 않는가
- 확장성(Scalability Curve)
  - 작업 수 증가에 따라 성능이 완만하게 저하되는가, 특정 지점에서 급격히 무너지는가
- 블로킹 구간의 영향
  - `synchronized`, native call, pinning 등 특정 구간이 전체 실행 모델에 어떤 영향을 주는가

## 개발 생산성 관점

- 코드 단순성
  - 동기식 스타일 유지가 쉬운가
  - 비동기 조합과 fan-out/fan-in 작성이 쉬운가
- 구조화된 동시성 지원
  - 부모-자식 작업 관계를 안전하게 관리할 수 있는가
- 취소와 타임아웃 처리
  - cancellation 전파가 자연스러운가
  - timeout 정책을 일관되게 적용하기 쉬운가
- 오류 전파 방식
  - 예외가 어떤 경로로 전파되는가
  - 일부 작업 실패 시 전체 작업을 어떻게 정리하는가

## 운영 관점

- 디버깅 난이도
  - stack trace, thread dump, coroutine dump가 얼마나 해석 가능한가
- 관측 가능성(Observability)
  - 메트릭, tracing, profiling 도구와 잘 연동되는가
- 라이브러리 호환성
  - 기존 blocking 라이브러리와 자연스럽게 연결되는가
  - 프레임워크가 해당 모델을 잘 지원하는가
- 운영 안정성
  - 잘못된 설정이나 특정 코드 패턴이 병목이나 장애로 이어질 가능성이 큰가

## 실험 시나리오

### 1. I/O Bound

- `sleep` 기반 synthetic benchmark
- HTTP 클라이언트 호출
- 파일 읽기/쓰기

확인할 것:

- 처리량
- 평균 응답 시간
- p95, p99 지연시간
- 메모리 사용량

### 2. CPU Bound

- 해시 계산
- 대량 JSON 파싱
- 수치 연산

확인할 것:

- CPU 사용률
- 스케줄링 오버헤드
- 동시 작업 증가 시 성능 변화

### 3. Mixed Workload

- 짧은 계산 후 외부 API 호출
- DB 조회 후 후처리

확인할 것:

- 실제 서비스와 유사한 상황에서의 응답 시간
- I/O 대기와 계산이 섞일 때의 안정성

### 4. Massive Fan-out / Fan-in

- 작은 작업 수천~수만 개 생성 후 결과 수집

확인할 것:

- 작업 생성 비용
- 합류(join) 비용
- cancellation 전파 비용

### 5. Cancellation Heavy

- 짧은 timeout
- 중간 취소 빈번
- 일부 실패 시 전체 정리

확인할 것:

- 취소 전파 속도
- 리소스 누수 여부
- 코드 복잡도

## 비교 시 주의할 점

- 같은 워크로드를 사용해야 한다.
- 같은 JVM 버전, 같은 머신, 같은 힙 설정을 사용해야 한다.
- 워밍업과 측정을 분리해야 한다.
- 평균값만 보지 말고 p95, p99를 함께 봐야 한다.
- synthetic benchmark와 실제 애플리케이션 시나리오를 구분해야 한다.

## 해석 가이드

- 코루틴이 유리한 경우
  - 구조화된 동시성이 중요할 때
  - 취소와 timeout 제어가 핵심일 때
  - fan-out/fan-in 패턴이 많을 때
- 가상 스레드가 유리한 경우
  - 기존 blocking 코드와 라이브러리를 많이 재사용해야 할 때
  - thread-per-request 모델을 단순하게 확장하고 싶을 때
  - Java 생태계와의 자연스러운 통합이 중요할 때

핵심은 "어느 쪽이 절대적으로 더 좋다"가 아니라, 워크로드와 팀의 운영 방식에 따라 더 적합한 모델이 달라진다는 점이다.
